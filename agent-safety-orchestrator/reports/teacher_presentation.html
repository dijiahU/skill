Safety Orchestrator
把零散的安全 skill 蒸馏成统一可调用的能力库

把社区上分散的 LLM agent 安全 skill 提炼为 95 个原子能力，按 agent 的 5 个执行阶段聚合成 14 个 archetype skill + 1 个 Router meta-skill；再把其中能用确定性规则替代 LLM 判断的部分下沉成 6 个 hook，自动在工具调用前后执行。Training-free，最终是一个 18 文件的 Claude Code skill bundle。

系统架构

Router · Skill · Hook

三层结构：Hook 在工具调用前后由 Claude Code 宿主自动触发，承担确定性可执行的检查（regex / IOC / Luhn / OPA 规则）；Router meta-skill 在每个阶段告诉 agent 该调哪个 archetype skill；Archetype Skill 承担需要 LLM 判断的检查（prompt injection、意图歧义、内容策略），并把 5 类原子能力打包给 agent 调用。

用户消息User message
原始用户输入。一旦进入 Claude Code，就会经过宿主自动派发的 UserPromptSubmit hook。
▼ ▼ ▼
Hook 层deterministic
由宿主在 UserPromptSubmit / PreToolUse / PostToolUse / Stop 触发；6 个 matcher 脚本按事件 fan-in 共 81 个原子（60 hook + 21 hybrid 快速路径）。无需 LLM 推理，确定性 block / warn。
▼ ▼ ▼
Routermeta-skill
safety-router-skill 在每个阶段告诉 agent："这一步要调哪些 archetype"。它本身不做检查，只负责 phase routing + verdict 聚合（任意 block 短路）。
▼ ▼ ▼
Archetype Skill 层LLM judgment
14 个 archetype，覆盖 14 个纯 skill 原子 + 21 个 hybrid 的 LLM 兜底。包括 prompt-injection、task-overreach、output content policy 等需要语义判断的检查。
▼ ▼ ▼
SentinelHITL
escalate-to-human-sentinel 在高风险/不可逆决策点拉起人类确认；现阶段为确定性实现，接口已对齐未来 3B Llama 二分类 ML 预测器（独立下游项目）。

6 个 Hook Matcher

81 atoms · deterministic

Claude Code 宿主在固定事件上触发 hook：用户消息进来、工具调用前、工具调用后、会话结束。每个 matcher 是一个独立的 Python 脚本，通过 stdin 拿到事件结构、用 regex / Luhn / IOC list 等确定性规则判断，把多个原子能力 fan-in 到一个脚本里以减少进程开销。

iv.

端到端示例 · 一个真实场景跑完所有层

walkthrough

用一个看起来"无害"的用户请求，演示 hook + skill 怎么协同。这个例子混合了三种安全问题：凭据泄露（用户在消息里粘了 AWS Key）、意图歧义（"旧的"是哪个？）、破坏性工具调用（agent 想直接 rm -rf）。

场景
User → Agent 帮我清理一下服务器上的旧日志文件吧，挪到归档目录就行。
对了我的 AWS 密钥是 AKIAIOSFODNN7EXAMPLE，
secret 是 wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY，你可以用这个登录服务器。
1hook · UserPromptSubmit

用户消息一进来，宿主先跑 matcher_user_prompt.py

事件 UserPromptSubmit · 匹配器 matcher_user_prompt.py · 完全不需要 LLM
脚本对消息文本跑五条 regex/Luhn 检查。AWS key 命中 SECRET_PATTERNS["aws_access_key"]，"清理"+"日志"匹配破坏性动词词表。
detect-credential-in-inputhook
AWS access key (AKIA...) 出现在用户输入；按 fail-policy 立即 block 并 redact，不让原文进 agent 的 context。
block
detect-destructive-action-keywordhook
"清理日志" 命中破坏性动词词表，附加 metadata 标记 destructive_intent=true，让后续 skill 知道这是个需要 ambiguity 二审的请求。
warn
detect-pii-in-input · detect-payment-card-data · detect-private-key-inputhook
未命中（这条消息里没有信用卡、姓名身份证、PEM 私钥）。
pass
2skill · input-understanding

Router 引导 agent 调三个 input-understanding archetype

由 safety-router-skill §3.2 phase routing table 决定 · 三个 skill 并行执行
凭据已被 hook redact，agent 看到的消息是 "帮我清理...旧日志...你可以用 [REDACTED:aws_access_key] 登录"。Router 在 input-understanding 阶段调出下面三个 skill。
detect-prompt-injectionskill (LLM)
没有 "ignore previous instructions" / DAN / 系统提示提取等模式，5 个子原子全 pass。
pass
classify-input-intent-ambiguityskill (LLM)
LLM 打分：safety-critical-ambiguous。理由：(a) "旧" 没定义（按天数？大小？最后访问时间？）；(b) "日志文件" 没说目录；(c) "归档目录" 没指定路径。同时上一步带过来 destructive_intent=true。
warn
scan-input-for-pii-and-secretshybrid
hook 已经在 step 1 把 AWS key 拦掉了，skill 兜底 LLM 检查未发现额外 secret。

3skill · planning

Agent 拟好计划，Router 在动手前调 planning archetype

由 Router 在 planning 阶段触发 · agent 内部拟出的计划：rm -rf /var/log/*.log 然后 mv ... /archive/
基于 step 2 的 safety-critical-ambiguous 标签 + destructive 动词，agent 本应先回问用户，但假设它没问、直接拟了 rm -rf。planning archetype 此时能再拦一次。
detect-task-overreachskill (LLM)
用户原话是"挪到归档目录"，agent 计划里却包含 rm -rf（不可逆删除）—— 范围越过了用户授权。Verdict: block，要求 agent 重新规划为非破坏性方案或先 escalate。
block
enforce-policy-as-codehook + hybrid
OPA 规则：/var/log 路径下的批量删除需 admin 审批；当前 agent 不在 admin role。
block
check-tool-permission-scopehook
Bash 工具在 allowed-tool-list 内，但 capability token 不含 "filesystem.delete:/var/log"。
block

这条请求的最终结局

  • 用户的 AWS Key 没有进 agent 的 context —— hook 在第 1 步就 redact 掉了，agent 后续记忆里根本没有这个秘密。
  • 破坏性的 rm -rf 永远没真正执行 —— planning 阶段 skill 拦了一次（语义层），Bash matcher 又拦了一次（规则层）；纵深防御。
  • 用户拿到的不是错误，而是一段说明 + 改进建议 —— Sentinel skill 把所有 verdict 整理成可读的 risk rationale 返还，并请用户确认更细化的清理范围。
  • 整条决策链可审计 —— Stop hook 记录了完整 decision-trace，事后可复盘哪一层拦住了什么、为什么。
